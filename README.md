# 🎢 كوكي بارك — Malahy

**نظام قطع التذاكر وحساب المبيعات اليومية** للمدينة الترفيهية — تطبيق سطح مكتب (Windows) بواجهة عربية كاملة (RTL).

**الإصدار الحالي:** `2.5.1` · **الحد الأدنى المسموح للترخيص (Floor):** `2.5.1` · **الهدف:** Windows x64 (NSIS)

---

## نظرة عامة

تطبيق «كوكي بارك» مخصص لقطع تذاكر المدينة الترفيهية وحساب المبيعات اليومية بشكل دقيق وفوري،
مع تقارير قابلة للتصدير والطباعة، ونظام تفعيل يحمي النسخة المثبّتة، وبوابة تحديث إلزامية
تضمن تشغيل أحدث إصدار دائمًا على الأجهزة.

## الميزات الرئيسية

- **قطع التذاكر** — إصدار تذاكر سريع مع طباعة الإيصال مباشرة على الطابعة المختارة.
- **حساب المبيعات اليومية** — تتبّع دقيق للمبيعات والمصروفات والهدايا مع أرصدة محدّثة لحظيًا.
- **التقارير** — تصدير بصيغة PDF و Excel (CSV) مع دعم كامل للغة العربية.
- **قاعدة بيانات محلية** — تخزين كل البيانات في ملف JSON داخل مجلد بيانات المستخدم،
  لا تتأثر بمسح بيانات المتصفح وتبقى محفوظة بعد التحديث.
- **نظام التفعيل (Activation Lock)** — غطاء تفعيل مقفول لا يمكن تجاوزه إلا بكود التفعيل الصحيح،
  مع فخ تركيز (focus trap) ومنع الوصول للواجهة خلفه (`inert` + `aria-hidden`).
- **بوابة التحديث الإجباري (Mandatory Update Gate)** — عند توفر إصدار أحدث لا يمكن فتح
  الواجهة الرئيسية حتى يكتمل التحديث؛ شاشة مقفولة بدون أي خيار للتخطّي.
- **التحديث التلقائي** — يعتمد على GitHub Releases لجلب أحدث إصدار وتنزيله وتثبيته تلقائيًا.
- **قفل نسخة واحدة** — منع تشغيل أكثر من نسخة من البرنامج في نفس الوقت.
- **حماية أدوات المطوّر** — تعطيل F12 / Ctrl+Shift+I في نسخة الإنتاج.

## بنية المشروع

```text
.
├── main.js              العملية الرئيسية (النوافذ + IPC + المنطق + التحديثات)
├── preload.js           الجسر الآمن بين الواجهة والعملية الرئيسية (contextBridge)
├── database.js          التخزين المحلي (ملف JSON واحد + نسخة احتياطية تلقائية)
├── activation.js        منطق غطاء التفعيل (مكتفٍ ذاتيًا، لا يلمس باقي التطبيق)
├── update-gate.js       منطق بوابة التحديث الإجباري (نقي وقابل للاختبار بدون Electron)
├── index.html           الواجهة الرئيسية (العمليات بالكامل)
├── windows/
│   ├── splash.html      شاشة البدء
│   └── update.html      شاشة التحديث الإجباري المقفولة
├── assets/              الأيقونات والصور
├── electron-builder.yml إعداد البناء والنشر
├── package.json         إصدار التطبيق والاعتمادات
└── .gitignore           ملفات مستثناة من Git (مخرجات البناء، البيانات، الأسرار)
```

> **ملاحظة:** مجلدات `dist/` و `releases/` و `node_modules/` وملف `opencode.json`
> محلية فقط ومستثناة من Git عبر `.gitignore`.

## التشغيل المحلي (التطوير)

```bash
npm install        # تثبيت الاعتمادات
npm start          # تشغيل التطبيق في وضع التطوير
```

في وضع التطوير يتم **تخطّي بوابة التحديث الإجباري تلقائيًا** (لأن `electron-updater`
يحتاج تطبيقًا معبّأً ليعمل)، وتبقى الواجهة الرئيسية متاحة دائمًا.

## البناء والإصدار

```bash
npm run dist       # بناء مثبّت NSIS x64 بدون النشر (يُنتج dist/malahy-setup-2.5.1.exe)
npm run publish    # بناء + نشر تلقائي على GitHub Releases
```

- يقرأ `electron-builder` الإعداد من `electron-builder.yml` (المزوّد: GitHub،
  المستودع: `sliveamer20/malahy`) وينتج `latest.yml` إلى جانب المثبّت ليعتمد عليه
  `electron-updater` في فحص التحديثات.
- **توكن النشر (GitHub token) يجب أن يأتي من متغيّر بيئة (مثل `GH_TOKEN`) ولا يُكتب
  في أي ملف داخل المستودع أبدًا.**

> ⚠️ **سياسة النشر:** لا تُبنى أو تُنشر إصدارات جديدة إلا بعد مراجعة كود وتحديث
> `version` في `package.json` و `FLOOR_VERSION` في `update-gate.js` معًا.

## متغيّرات البيئة والإعداد المحلي

| المتغيّر | النوع | الوصف |
| --- | --- | --- |
| `MALAHY_TEST_GATE=1` | اختياري | يجبر تشغيل **بوابة التحديث الإجباري** في وضع التطوير (لا يعمل بدون تطبيق معبّأ عادةً). |
| `GH_TOKEN` / `GITHUB_TOKEN` | عند النشر فقط | توكن GitHub المستخدم من `electron-builder` للنشر على Releases. **لا يُخزّن في المستودع.** |

**لا يوجد أي متغيّر بيئة إجباري لتشغيل التطبيق العادي.** كل إعدادات التطبيق تُحفظ
في مجلد بيانات المستخدم:

- **البيانات:** `%APPDATA%\كوكي بارك\malahy-data.json`
- **نسخة احتياطية تلقائية:** `%APPDATA%\كوكي بارك\malahy-data.bak.json`
- **سجل الأخطاء:** `%APPDATA%\كوكي بارك\malahy-errors.log`

## نظام التفعيل (Activation Lock)

- عند أول تشغيل تظهر **تغطية تفعيل مقفولة** فوق الواجهة بأكملها (`#actOverlay`).
- التغطية تعطّل كل عناصر الصفحة خلفها (`inert` + `aria-hidden`)، وتلتقط التركيز
  (focus trap) بحيث لا يخرج مفتاح `Tab` منها، وتمنع كل الأحداث عليها.
- يتم التحقق من كود التفعيل محليًا (offline) داخل `activation.js`، ويتم حفظ حالة
  التفعيل في قاعدة البيانات المحلية تحت المفتاح `malahy_activated`.
- للتواصل والحصول على الكود: زر واتساب داخل التغطيرة.

> 🔐 **ملاحظة أمنية:** التحقق من التفعيل يتم **محليًا بالكامل** (offline) لأن
> التطبيق يعمل بدون خادم. كأي تحقق من هذا النوع، فإن الكود يُشحن مع التطبيق،
> لذا هو **تشغيل تحوّط (obfuscation) وليس تشفيرًا حقيقيًا** — وهذه طبيعة
> أنظمة التفعيل غير المتصلة بالخادم. القيمة نفسها غير مخزّنة كنص صريح، لكن
> يجب اعتبارها حماية ضد الاستخدام العادي وليست حماية مطلقة.

## بوابة التحديث الإجباري (Mandatory Update Gate)

القاعدة الأساسية: **كل إصدار يُنشر على GitHub يُعتبر إلزاميًا.**

| الحالة | السلوك |
| --- | --- |
| النسخة المثبّتة ≥ النسخة المطلوبة | دخول طبيعي (حتى لو كانت الجهاز أوفلاين). |
| النسخة المثبّتة < النسخة المطلوبة والخادم متاح | تُفتح شاشة التحديث المقفولة → تنزيل تلقائي → إعادة تشغيل. |
| النسخة المثبّتة < النسخة المطلوبة والخادم غير متاح | شاشة مقفولة + رسالة «أوفلاين» + زر إعادة المحاولة. |

- **النسخة المطلوبة (required)** = أكبر قيمة بين `FLOOR_VERSION` (مدمجة في `update-gate.js`)
  وأحدث إصدار منشور على الخادم.
- **لا يوجد أي زر إغلاق أو تخطّي** للشاشة (`closable: false`)، والواجهة الرئيسية
  لا تُنشأ أصلًا طالما البوابة مفعّلة، فلا يوجد ما يمكن تخطّيه إليه.
- `update-gate.js` نقي (pure) وقابل للاختبار بدون Electron.

## آلية التحديث التلقائي (GitHub Releases)

1. التطبيق يقرأ إعداد النشر من `electron-builder.yml` (المزوّد: GitHub).
2. يفحص `latest.yml` المنشور مع كل إصدار على GitHub ويقارن رقم الإصدار.
3. عند توفر إصدار أحدث: تُفتح بوابة التحديث، ويُنزَّل التحديث ثم تُعاد
   التشغيل تلقائيًا — ولا يمكن الوصول للواجهة الرئيسية قبل اكتمال ذلك.
4. داخل الواجهة الرئيسية يبقى الفحص **اختياريًا** (لا يُقفل البرنامج).

### أبرز تغييرات `2.5.1`

- **إعدادات الورديات (قابلة للضبط):** قسم جديد «إعدادات الورديات» في الإعدادات
  يتيح للمسؤول تغيير وقت بداية ونهاية كل من **الوردية الأولى** و**الوردية الثانية**
  (اختيار الوقت من نظام ويندوز مباشرةً)، مع **معاينة فورية** للوردية النشطة الآن
  و**تحقق حيّ** يرفض أي جدول غير صالح (وقت ناقص، صيغة خاطئة، مدة صفرية، أو
  **تداخل/تعارض** بين الورديتين) برسالة واضحة، ولا يُسمح بالحفظ حتى يصبح الجدول
  سليمًا. يُحفظ الجدول على الجهاز ويبقى بعد إعادة التشغيل والتحديث.
- **مصدر واحد للحقيقة:** كل ما يعتمد على الورديات يقرأ من الإعدادات فقط —
  كشف الوردية النشطة واسمها وعرضها في الرأس، التقارير والفلاتر، حسابات
  اليوم والوردية، وحدود يوم العمل. لا يوجد أي مكان يكرّر أوقاتًا ثابتة.
- **دعم عبور منتصف الليل:** الوردية الثانية يمكنها الامتداد بعد منتصف الليل
  (مثلًا 7:00 م ← 2:00 ف) ويعمل النظام بشكل صحيح لأي جدول صالح.
- **التوافق مع الإصدارات السابقة:** المستخدمون الذين يرتقون من `2.5.0`
  يبدؤون تلقائيًا بالجدود الحالي (أولى 10:00 ص → 7:00 م / ثانية 7:00 م → 2:00 ف)
  ولن يحصلوا على جدول فارغ أو مكسور أبدًا.
- **تصميم تذكرة جديد:** إعادة تصميم التذكرة بالكامل لتظهر كمذكرة دخول احترافية
  لمدينة ألعاب — أبيض وأسود فقط (مناسب للطابعات الحرارية 58مم/80مم والعادية A4)،
  مع هيدر زخرفي وصناديق بحواف دائرية وفواصل متقطّعة وخط عربي قوي. **كل البيانات
  ديناميكية** من عملية البيع الفعلية: اسم النشاط من نظام الهوية، اسم اللعبة،
  عدد التذاكر، سعر التذكرة، الإجمالي، طريقة الدفع، رقم التذكرة، والتاريخ والوقت.
- **إشعار دائم:** «التذكرة لا ترد ولا تستبدل» يظهر على **كل تذكرة** كعنصر تصميمي
  ثابت أسفل التذكرة بخط واضح لا يتداخل أبدًا مع البيانات أو رمز QR.
- **رمز QR اختياري:** ميزة جديدة تمامًا (مُغلقة افتراضيًا) تُظهر رمز QR لتعيين
  الموقع عبر رابط خرائط Google قابل للضبط من الإعدادات. لا يمكن تفعيلها بدون
  رابط صحيح، ولا تؤثر على أي حسابات أو منطق بيع. تُولَّد بدون إنترنت (مكتبة
  مضمَّنة) وتظهر بمساحة بيضاء كافية لتكون مقروءة على الطابعات الحرارية.
- **تذكرة الهدية:** استخدمت نفس تصميم التذكرة الجديد مع الحفاظ على منطق
  الهدايا بالكامل كما هو.
- **الاستقرارية والحماية:** الحفاظ على نظام التفعيل وبوابة التحديث الإلزامي
  والمبيعات والتذاكر وإدارة الألعاب والتقارير والموظفين والرواتب والطابعات
  كما هي في `2.5.0` (الحد الأدنى للترخيص رُفع إلى `2.5.1`).

### أبرز تغييرات `2.5.0`

- **هوية النشاط (الاسم + الشعار):** إضافة قسم «هوية النشاط» في الإعدادات
  يتيح تغيير **اسم الملاهي** و**اختيار شعار جديد** مع **معاينة فورية**،
  و**استعادة الشعار الافتراضي**. يُحفظ الاسم والشعار على هذا الجهاز ويبقيان
  بعد إعادة التشغيل، ويظهران فورًا في رأس البرنامج وعلى التذاكر والتقارير
  وكشوف الرواتب. لا يُسمح باسم فارغ، ويُفضّل PNG الشفاف (الحد 5 ميجا).
- **مصدر واحد للاسم:** كل أماكن عرض الاسم تقرأ من دالة واحدة (`brandName()`)
  بدل تكرار الاسم الثابت، مع الحفاظ على القيمة الافتراضية «كوكي بارك».
- **رأس البرنامج — الوضع الداكن:** إصلاح قراءة **التاريخ** في الوضع الداكن
  (كان رقم اليوم باهتًا): لون أوضح للنص، ورقم اليوم بارز ومنفصل بصريًا.
- **سهم الوردية (RTL):** تصحيح اتجاه سهم نطاق وقت الوردية في واجهة RTL
  ليُشير لليسار (`←`) بدل اليمين (`→`). **القيم وترتيبها المنطقي لم يتغير** —
  تغيّر شكل الحرف فقط (أولى 10ص←7م / ثانية 7م←2ف / بين 2ف و10ص لا توجد وردية).
- **الاستقرارية والحماية:** الحفاظ على نظام التفعيل وبوابة التحديث الإلزامي
  والمبيعات والتذاكر وإدارة الألعاب والتقارير والموظفين والرواتب والطابعات
  كما هي في `2.4.9` (الحد الأدنى للترخيص رُفع إلى `2.5.0`).

  التاريخي عند البيع، ومنع بيع الألعاب المعطّلة.
- **الطابعات:** دعم الطابعات العادية (A4) والطابعات الحرارية 58مم/80مم مع
